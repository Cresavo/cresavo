- **Server-side journals for account salons, prepared and off by default.** With `JOURNALS_ON_SERVER=1` and `JOURNAL_ENCRYPTION_KEY` (`v1:` plus 32 random bytes in base64), journal text is kept encrypted at rest in a new table, `journal_entry` (AES-256-GCM per version, the associated data binding each version to its salon, customer, entry and version), and the salon the browser receives holds only stubs: id, customer, date, staff member and the number of versions. The customer page fetches that customer's journal from `GET /api/owner/journals?customer=…` with a short loading state, and the server logs that read in the same transaction (replacing the whole-salon read log); the customer data export reads the journal the same way. Adding and editing go through `POST /api/owner/journals` and the store's usual action path, so undo, idempotency and the audit log keep working, while the audit log keeps the entry id instead of the text. Every edit appends a version; a customer moved to the trash marks their entries' rows, and restoring unmarks them. Erasing a customer deletes their rows in the same transaction (also through `erase_subject`), and a version of another customer's entry that names them is replaced by a scrubbed copy. Journals already in a salon's document move into the table on the first load or save with the flag on, once, under the salon's lock; the stored replays and the audit rows from before lose their text in the same transaction, and only then is the salon marked as moved. Every account change, the journal routes and erasure are bound to the login the salon was loaded in (a new sign-in gets a new session key), so a stale tab of another account or an earlier sign-in is refused, and only the server's own reads are logged. A key is checked against a verifier stored for its version before it is used. With the flag on and no working key, the journal routes answer 503, salons are served without journal text, and while a salon's document still holds journal text every change to it is refused; nothing falls back to plaintext. A salon with encrypted journals is only erased with the key, also with the flag off. Rollout note: an owner tab left open on the previous build gets 409 on every save until it is reloaded (owner accounts are not live yet, so this affects no one); after a login change the studio now reloads the page itself. With the flag off nothing changes, and the demo is untouched. New migration `20261123090000_server_journals`; run `prisma/grants/roles.sql`, `erase-subject.sql` and, where row-level security is on, `rls-enable.sql` again after deploying it (the table gets the tenant policy and no support access). Losing the key makes stored journals unreadable and there is no rotation tool yet (docs/operations/INCIDENT_RUNBOOK.md). English and Swedish.

- **An "About us" section on the booking page.** A business can now describe itself in its own words: a heading and a few paragraphs of plain text (up to 1,500 characters; line breaks are kept and an empty line starts a new paragraph, with no HTML or Markdown). The owner switches the section on under Booking page, moves it like any other section, picks a plain or card look and sees it in the live preview; an empty heading reads "About <business name>", and the section stays hidden until there is text. It is off on every existing page. A freshly started demo of Salong Eko shows it after the team with invented text in English and Swedish. The assistant understands "add an about us section" and "ta bort om oss". The server validates the text with `page/set`, which now requires the page's `about` field, and a text whose section is off is never sent to the public page.
- **Database-level tenant isolation for the studio store, prepared but not yet enforced.** Every store transaction now sets its tenant first, transaction-local so a pooled connection never carries it into the next request, and a web worker's delivery after a commit stays in the tenant it wrote. A new migration (`store_rls_policies`) adds fixed SECURITY DEFINER functions for the effect outbox and the retention sweeps, closed to PUBLIC and naming no role, so it runs on any database without extra setup; the code uses them whether or not row-level security is on. The `effects:drain` poller gets a role and login of its own (`cresavo_outbox`) and, like the sweeper, needs no privilege on the store tables: the poller's functions act only on the effect its claim names and read a claimed message's salon as a view with only that booking, its customer, services and staff, and the sweeper's carry the retention cutoffs (a clock it passes can only make a sweep do less). Each claim gets a random token that every later read and write needs; writes take typed values instead of delivery JSON; a stored booking link must still lead to the booking's own page before a signed token is attached (otherwise the e-mail fails as `link_mismatch` for a person); a provider confirmation for a row settled meanwhile is kept apart (`late_confirmation`) instead of changing its status. The rate-limit sweeps are functions too, so the sweeper can never lift an active sign-in lock-out. A booking address resolves to a tenant id only (`store_salon_by_slug`), never to the salon's row. The migration adds the outbox columns `claim_token` and `late_confirmation`. Row-level security here is defence in depth against query bugs, not against a compromised web credential, which sets its own tenant. An operator enforces RLS with `prisma/grants/rls-enable.sql`: after `bootstrap-roles.sql` (the NOLOGIN group roles) and the grants files, it locks the four tables, creates the policies (each naming its roles; a sandbox token resolves only by its full hash, a booking address to one salon), checks that they are exactly the expected set and enables and forces RLS in one transaction; `rls-disable.sql` turns it off and drops the policies. `verify-rls.sql` reports the state and finds every runtime login that could bypass it, and `verify-roles.sql` compares each login's effective table, column and function privileges with a complete allowlist. Backups under RLS need a BYPASSRLS backup login or the table owner with `pg_dump --enable-row-security`, and restoring a dump that carries policies onto a fresh cluster runs `bootstrap-roles.sql` first (docs/operations/BACKUP_RESTORE.md). Change notifications now carry an opaque tag instead of the tenant id and version; a listener reads the version in the tenant's own scope, at most one read in flight per tenant. Run `roles.sql` and `studio-store.sql` again after deploying this, and point `DATABASE_URL` of `effects:drain` at the outbox login before enabling RLS. Nothing changes for salons or the demo until that step runs.
- **A photo library and logo upload for owner accounts (behind `OWNER_ACCOUNTS_ENABLED`).** A Photos page, reached from Campaigns and the poster's photo choice, takes photos from the phone or computer (the camera too), with a description, delete with undo for a day, and "Use in campaign". Booking page › Logo stores an account's logo there; it stays private (the owner's preview only) until the page is saved, and saving retires the logo shown before. An account salon's page no longer takes a new inline logo. Library photos can be picked for a poster and are saved with the campaign; the poster renderer reads them itself for the owner's own business. Only complete still JPEG, PNG and WebP images are accepted, recognised from the bytes (HEIC is turned into JPEG in the browser when it can be read; SVG and animated images are refused), and each is rebuilt from an allowlist without re-encoding: EXIF with GPS, XMP, IPTC, comments, thumbnails, C2PA manifests and appended images are left behind. Limits: 8 MB per file, 300 photos, 500 MB of storage per business (deleted pictures count until purged), 60 uploads per 15 minutes; the same picture is kept once. Photos are served only to the signed-in owner; only the published logo has a public address (its id and hash), revalidated after five minutes. The studio's picture caches are kept to one session. With S3, uploads are recorded as pending first so the sweep finds any that fail. The bytes are stored in Postgres by default, or in an S3-compatible bucket with `MEDIA_STORE=s3` and `MEDIA_S3_*` (SigV4 signed with `node:crypto`, no new dependency). `npm run store:sweep` purges deleted pictures after 30 days. The public demo shows its sample photos and explains that the library needs an account. New migration `20261122170000_media_library`; run `prisma/grants/roles.sql` again after deploying it. Storage, EU choice and backups: `docs/operations/MEDIA_STORAGE.md`. English and Swedish.
- **Book for someone else.** The contact step of the booking page asks "Who is the visit for?" with "For me" chosen from the start, so a booking for yourself takes no extra tap. "For someone else" adds one field for the visitor's name; the booker stays the contact person and receives the confirmation and reminders, which now say who the visit is for. The booking keeps the visitor's name (`visitFor`) beside the customer who booked, and the Studio shows the visitor on calendar and Today rows and in the booking sheet, with "Booked by" and the contact's phone. A visit for someone else keeps the booker's own details out of it: the booking sheet and Today show the booker's name and phone but not their note, tags, history or journal advice, marking the visit done does not use the booker's punch card, and My bookings and the cancel and move dialogs say who the visit is for. The visitor's name is treated as a second person's data: erasing a customer removes their name from other people's visits, checkouts and sent messages, the booker's data export puts such visits under "review before sending", and the assistant never sends the name to a model. Contact names are limited to 80 characters and phone numbers to 20, as on a salon's public page. Offered for salons kept in the browser (the demo and an own salon); salons kept on the server do not offer it yet, because their erasure of a customer does not cover the new name.
- **Two-step sign-in for owner accounts (behind `OWNER_ACCOUNTS_ENABLED`).** An owner can turn on a code from an authenticator app (TOTP, RFC 6238: six digits, 30 seconds, one step either side) on `/account`: confirm the password, scan the QR code or type the key, enter the first code, and save ten single-use recovery codes that are shown once (copy and download). Sign-in then asks for the code, or a recovery code, after a correct password; no session exists until then. Each code works once, also when two requests race; wrong codes count toward the same lock-out as wrong passwords, and only a correct second step clears it. Turning it on or off ends every other session, and new recovery codes replace the old ones. A password reset keeps two-step sign-in on. The secret is stored encrypted (AES-256-GCM) and the recovery codes as scrypt hashes salted per account, both under the new `OWNER_MFA_KEY`; without it, setup and the sign-in of an enrolled account answer "not configured" and are never skipped. `OWNER_MFA_REQUIRED=1` (off by default) limits an account without two-step sign-in to setting it up. Each session records that it passed the second step and an enrolled account's session without it is refused, and each correct password leaves a one-time challenge (at most five per account) that is checked, spent and turned into a session in one transaction; "Sign out everywhere" now also raises the credential version, ending sessions and challenges in the same step. New migration `20261122140000_owner_mfa`; run `prisma/grants/roles.sql` again after deploying it. Do not roll back to a build before this one once an owner has turned two-step sign-in on: older builds would accept password-only sessions. English and Swedish ("Tvåstegsverifiering").
- **Monitoring, ready but off until configured.** `GET /api/health` returns `{ ok, version }` for an uptime monitor, and runs a database check with a short timeout only when `HEALTH_CHECK_DB=1`. With `ERROR_REPORT_DSN` set to a Sentry-compatible DSN (choose an EU region), unexpected 500s and errors Next.js catches (`onRequestError`) are sent once each as an envelope over plain `fetch`, with a 2-second timeout and `ERROR_REPORT_SAMPLE_RATE` sampling: error class, stack file paths, route pattern, release, environment and event code, never messages, bodies, headers, cookies, query strings, e-mails or IPs. Without the DSN nothing is sent. Setup, alerts and uptime checks are in `docs/operations/MONITORING.md`; the pilot gate item stays open.
- **Pause booking e-mail and reconcile the outbox (operators).** `CONCEPT_EMAIL_PAUSED=1` holds every booking e-mail: neither the `effects:drain` poller nor a web worker's drain after a commit claims one, so due e-mails stay pending without using an attempt and none becomes `failed` however long the pause lasts; unset it and they go out. Booking and the staging of e-mails are unchanged, and SMS and payments keep being delivered. `npm run effects:reconcile` lists `failed` and `uncertain` e-mails per tenant (id, kind, age, attempts, last error code, recipient's domain only, never a body or an address) and, only with `--apply` and for the `--tenant` named, retries a failed e-mail that never left (the same frozen message, link, sender and reply-to; one that may have left only with `--force-maybe-duplicate`) or settles an uncertain one as sent or not sent after a look at the provider's log. A retry is refused for a booking that is gone, cancelled or erased (checked under the salon's lock) and for a message retention has purged, and the deliverer itself now fails such a purged snapshot for a person before it marks or sends anything. The pause is also checked for a row already claimed, before any sink runs and again right before the provider call. Each change runs under the row's lock, within the named tenant only, is idempotent and prints one JSON audit line. A failed attempt now keeps an allowlisted error code on the e-mail's delivery record. An outbox row's attempt counter never goes down any more: a deferral or a retry moves a separate `attemptBase` instead, so a stalled worker can never write over a newer claim. A send the pause holds after it was marked `dispatched` gives the marker back in the same write that releases the row, and a request that never started gives it back even after a timeout failed the row, so an unsent e-mail never looks uncertain. Resend's 23-hour replay window now counts from the first request that may have reached the provider (`submittedAt`, which a request refused outright does not set), not from the first rendering, and `list` shows when each message was rendered and first submitted, the window an operator searches in the provider's log. A send marked uncertain or `reconcile` keeps its frozen message until delivery is confirmed or retention blanks it, so one confirmed as not sent can be resent unchanged with `retry --force-maybe-duplicate`. A `reconcile` row (a reused key) can be settled with `mark-sent` or `mark-failed`; a retry refuses a move notice of a cancelled booking and a row rendered once whose snapshot is gone (`snapshot_missing`); `--actor` is a short lower-case staff handle, never six digits or more however separated. **Every drain worker, web worker and the CLI must run this version before `effects:reconcile retry` is used**: an older deliverer ignores `attemptBase`. No deployment sends live e-mail yet. The incident runbook recommends the pause instead of switching `CONCEPT_CONNECTIONS_LIVE` or the provider off. No migration.
